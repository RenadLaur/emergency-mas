# Архитектура MVP

## Архитектурное решение

MVP строится как Python-симулятор вокруг SUMO. SUMO отвечает за микроскопическое движение транспортных средств. Python через TraCI управляет сценарием и агентами, считывает состояние сети, меняет маршруты и фазы светофоров, создаёт инциденты и записывает экспериментальные результаты. Для пакетных экспериментов предпочтителен libsumo; TraCI сохраняется для интерактивной отладки и визуализации в SUMO-GUI.

```
Scenario configuration and seed
            |
            v
Experiment runner --> Simulation orchestrator <--> SUMO via TraCI or libsumo
                         |       |       |              |
                         v       v       v              v
                    Dispatcher Routing Driver       Traffic light
                         |                            controller
                         v
                    Incident manager
                         |
                         v
               Event log and metrics store --> analysis and reports
```

## Слои

| Слой | Ответственность |
| --- | --- |
| `simulation/` | SUMO-конфигурации, сети, маршруты, сценарии, погода и адаптер TraCI/libsumo |
| `agents/` | Доменные агенты и детерминированные правила без зависимости от RL-фреймворка |
| `ai/baselines/` | Ближайшая свободная машина, Dijkstra, A*, traffic-aware routing |
| `ai/env/` | Gymnasium/PettingZoo-обёртка, пространства наблюдений/действий и награды |
| `ai/training/`, `ai/policies/` | PPO/MAPPO, конфигурации обучения и чекпоинты |
| `experiments/` | Матрицы сценариев, запуск серий, агрегация и графики; результаты не смешиваются с кодом |
| `tests/` | Юнит-, интеграционные и детерминированные seed-тесты |
| `backend/`, `frontend/` | Отложенный слой визуализации результатов; не участвует в шаге симуляции |

## Доменные сущности и агенты

Dispatcher Agent хранит очередь вызовов с координатами, временем создания и уровнем приоритета, а также состояние парка. Он назначает машину по стратегии, а при её недоступности инициирует переназначение.

Emergency Vehicle Agent представляет миссию машины: путь к вызову, текущий статус, маршрут, тип, состояние доступности и связанного Driver Agent.

Routing Agent выбирает или пересчитывает путь с учётом времени проезда, заторов, погоды и закрытых рёбер. В MVP он является сервисом принятия решения, а не обязательно независимым RL-агентом.

Driver Agent обновляет стресс, усталость, внимательность и время реакции. Его состояние влияет на безопасную скорость и риск. Изначальные параметры семплируются около базового профиля из seed.

Traffic Light Agent предоставляет приоритет выбранной экстренной машине с ограничением по времени и безопасным возвратом в стандартную программу.

Incident Agent создаёт и завершает вызовы, ДТП и дорожные блокировки, а также сообщает об изменениях маршрутизатору и диспетчеру.

Обычные водители моделируются параметрами SUMO и небольшой Python-логикой уступания, а не отдельными RL-агентами.

## Шаг симуляции

На каждом шаге оркестратор сначала применяет запланированные события и управляющие действия, затем выполняет один шаг SUMO. После него он считывает положение, скорость, занятость полос, сигналы и столкновения; обновляет состояние водителей и показатели безопасности; проверяет необходимость перерасчёта маршрута, приоритета или переназначения. Все изменения записываются как события с номером шага и идентификатором запуска.

## Данные и воспроизводимость

Входы запуска — версия сети, файл сценария, параметры модели и корневой seed. От него детерминированно выводятся независимые генераторы для спроса, водителей, уступания и инцидентов. Выходы — машиночитаемый event log и таблицы per-run/per-call/per-vehicle. Обязательные поля: `run_id`, `seed`, версия сценария и сети, выбранные решения, причины переназначения, маршруты и метрики.

Формат начальных сценариев — YAML или JSON, результатов — Parquet или CSV. На этапе MVP допустимы файлы; PostgreSQL нужен только для dashboard или многопользовательского доступа.

## Модель безопасности

Безопасность — отдельная часть целевой функции, а не штраф после расчёта времени. TTC и near-miss рассчитываются с явно зафиксированными порогами. ДТП берутся из событий SUMO, если они доступны в данной конфигурации, и/или из прозрачной вероятностной модели риска. ДТП может сделать машину недоступной и создать блокировку; это запускает перерасчёт маршрута и переназначение.

## RL-граница

До RL все решения доступны как чистые правила с теми же входами и логами. Первой обучаемой политикой является PPO для ограниченного решения — назначения машины или выбора одного из кандидатов маршрута. Награда объединяет время прибытия, успех вызова, штрафы за риск и влияние на обычный транспорт. MAPPO добавляется после валидации среды: центральный critic и несколько обучаемых политик для диспетчера и маршрутизатора. Агент светофора остаётся правилом, пока не появится отдельный исследовательский вопрос.

## Внешние интерфейсы

OSMnx используется только в подготовительном конвейере данных: загрузка/фильтрация OSM и экспорт, после чего сеть конвертируется инструментами SUMO. Runtime симуляции не должен зависеть от сети. FastAPI и Next.js получают результаты через стабильные файлы или API, но не управляют симуляцией напрямую.
